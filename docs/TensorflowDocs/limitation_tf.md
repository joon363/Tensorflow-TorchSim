# TensorFlow 파이프라인 MLIR 문자열 파싱 한계점 보고서 (limitation_tf.md)

## 1. 개요
현재 구현된 `TENSORFLOW_MLIR_DIRECT_TEST` 연동 파이프라인은 XLA가 컴파일한 MLIR 파일(`tf-mlir.mlir`)을 읽어온 뒤, PyTorch 백엔드 및 C 시뮬레이션 하네스 규격에 맞춰 변환하는 가교 역할을 수행합니다. 이 과정에서 `transform_tf_mlir` 함수는 파이썬의 **정규식(Regex)**과 **직접적인 문자열 파싱(String Splicing)**을 사용하여 MLIR 코드를 수정합니다.

이 방식은 현재의 고차원 테스트 케이스들을 통과시키는 데에는 성공했으나, 컴파일러 프론트엔드의 버전 변경이나 미세한 구문 변화에 매우 취약한 기술적 구멍(loophole)들을 내포하고 있습니다. 본 보고서는 이러한 기술적 한계점과 구멍을 체계적으로 서술합니다.

---

## 2. 세부 기술적 한계점 및 구멍 (Technical Loopholes)

### 2.1 문자열 서식 및 정규식 취약성 (Syntactic Fragility)
MLIR 파일은 줄바꿈, 들여쓰기(공백/탭), 주석 배치, 다이얼렉트의 출력 서식(예: `func.func` 대신 생략형 표현 등)에 따라 텍스트 형태가 언제든지 달라질 수 있습니다.
* **구멍**: 현재 구현된 정규식 패턴(예: `func\.func\s+@([a-zA-Z0-9_]+)`)은 특정 공백 스타일이나 어트리뷰트 배치만을 가정합니다. 만약 컴파일러가 함수 정의부 뒤에 `attributes { ... }`와 같은 메타데이터를 추가하거나 공백의 형태를 바꾸면 정규식 매칭이 완전히 실패하여 컴파일 에러를 야기합니다.
* **예시**: `linalg.map` 블록 매칭 정규식은 매우 정교하지만, 블록 내부에 커스텀 주석(`// loc...`)이 삽입되거나 `linalg.yield` 구문 앞뒤에 공백이 추가되면 매칭되지 않아 파싱되지 않은 채 하부 컴파일러로 전달되어 결국 에러를 발생시킵니다.

### 2.2 인자 파싱의 불안정성 (Argument Parsing Mismatch)
함수의 매개변수 목록을 파싱하기 위해 구현된 `split_args`는 각 콤마(`,`)를 기준으로 문자열을 단순 분리하는 휴리스틱에 의존합니다.
* **구멍**: MLIR 인자 타입 내에 복잡한 레이아웃 어트리뷰트(예: `strided<[?, ?], offset: ?>`)나 메모리 공간 표시가 포함되고, 그 안에 콤마(`,`)가 중첩되어 들어가는 경우(예: `memref<2xf32, #map, memory_space = 1>`) `split_args`는 이 중첩 구조를 인지하지 못하고 콤마 단위로 인자를 조각내어 버립니다. 이 경우 함수 선언부가 심각하게 오염되어 시그니처 컴파일에 실패하게 됩니다.

### 2.3 단순 문자열 대체로 인한 이름 충돌 (Symbol Collision)
함수 이름을 `@main`에서 `@kernel`로 변경하거나 리턴값을 가로챌 때 문자열의 `replace` 또는 단순 치환 기법을 사용합니다.
* **구멍**: 연산 그래프 내의 텐서 이름이나 변수 이름에 하필 `main` 또는 `return`이라는 문자열이 부분적으로 포함되어 있는 경우, 변환기가 연산 기호나 피연산자 명칭까지 강제로 교체해 버려 의미론적(Semantics) 손상을 유발할 수 있습니다.

### 2.4 동적 형상(Dynamic Shape) 미지원
현재의 복사 루프 생성 코드는 형상(shape) 리스트를 정수형 리스트로 강제 변환하여 `arith.constant <값> : index` 형식으로 루프 바운드를 고정합니다.
* **구멍**: 입력 텐서 중 하나라도 동적 축(예: `memref<?x32xf32>`)을 가지는 경우, 문자열을 정수로 변환하는 코드(`int(x)`)에서 `ValueError`가 발생하여 컴파일 단계에 진입조차 하지 못합니다. 실제 프런트엔드 컴파일러는 배치 사이즈 등을 위해 동적 축을 빈번히 사용하므로 이는 심각한 확장성 제약입니다.

### 2.5 런타임 검증 결여 (Lack of Semantic Validation)
파이썬 변환기는 텍스트를 기계적으로 생성할 뿐, 해당 변환이 MLIR의 데이터 흐름 규격(SSA value dominance)이나 타입 정합성 규칙에 위배되는지 변환 시점에 전혀 검증하지 못합니다.
* **구멍**: 생성된 문자열에 괄호 누락이나 타입 명세 오타가 발생하는 경우, 파이썬 단에서는 오류를 감지하지 못하고 툴체인 최하부의 `mlir-opt`가 에러 메시지와 함께 비정상 종료(Assert)된 이후에야 사후적으로 문제를 분석해야 하는 개발 생산성 저하가 발생합니다.

---

## 3. 요약 (Conclusion)
문자열 기반의 애드혹(ad-hoc) 변환기는 신속한 기능 프로토타이핑에는 유용하나, 프레임워크의 프로덕션 레벨 안정성을 담보하기는 어렵습니다. 

이 문제를 근본적으로 해결하기 위해서는 MLIR 문법을 직접 이해하고 추상 구문 트리(AST) 수준에서 구조를 안전하게 조작할 수 있는 **MLIR Python Bindings (`mlir.ir.module`)**를 활용한 구조적 재설계가 강력히 권장됩니다.
